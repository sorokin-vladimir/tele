# Настройка

> Перевод [configuration.md](../configuration.md) на коммит `a8ea9ea`. Если перевод расходится с английской версией, верна английская.

`tele` хранит один файл YAML, который создаётся при первом запуске:

```text
~/.config/tele/config.yml
```

Чтобы использовать другой, передайте `--config <path>`.

<a id="the-settings-overlay"></a>
## Окно настроек

Клавиша `,` открывает окно настроек.
В нём все настройки `tele`, сгруппированные и упорядоченные так же, как в файле конфигурации, поэтому строку, которую вы видите там, найдёте в файле по тому же пути.
Для каждой показано текущее значение, помечены те, что никто не выбирал (`[default]`), и сказано, когда изменение вступит в силу: сразу, в следующий раз (`[next]`), когда `tele` будет делать это действие, после перезапуска (`[restart]`) или после перезапуска `tele`, который держит соединение (`[host restart]`).
Там же перечислены клавиши: что изменил ваш конфиг и что было до изменения.

Изменения оттуда записываются прямо в `config.yml`, с сохранением ваших комментариев, пустых строк и всего, о чём `tele` не знает.
Нет разницы, править файл в редакторе или в окне настроек: в обоих случаях файл затем перечитывается, так что они никогда не разойдутся.
`enter` меняет настройку под курсором, `r` возвращает значение по умолчанию, `esc` закрывает окно.

Четыре настройки показаны, но там не меняются: какой это аккаунт и где лежит его состояние.
Их изменение означает перенос файлов и новую сессию, поэтому это осознанная правка файла, а не одно нажатие клавиши.

Часть настроек принадлежит `tele`, который держит соединение с Telegram: ключ приложения, каталог состояния, прокси, размеры кэшей, сколько истории загружается за раз и системные уведомления.
Остальные принадлежат окну, на которое вы смотрите: тема, клавиши, тосты, отрисовка изображений.
Каждый `tele` читает свой вид настроек из своего файла конфигурации.
Окно, подключённое к другому `tele` (см. [Каталог состояния](#state-directory)), показывает настройки первого вида так, как их держит тот `tele`, и изменение, сделанное в окне, отправляется ему: он записывает его в свой файл конфигурации (это может быть не файл окна) и применяет.
Собственные настройки окна, как обычно, записываются в файл окна.

Если перечитать конфиг из окна, перечитываются оба: окно заново читает свой файл, а `tele`, который держит соединение, читает свой.
О проблемах, найденных любым из них, сообщается в одном уведомлении, и если один из них не принял свой файл, он так и говорит, не отменяя того, что принял другой.

<a id="configyml"></a>
## config.yml

```yaml
# proxy: # how tele reaches Telegram; absent means auto
#   type: mtproto # auto | direct | mtproto | socks5
#   server: 127.0.0.1
#   port: 1443
#   secret: ee... # mtproto only, hex or base64url
#   username: "" # socks5 only
#   password: "" # socks5 only

# state_dir: ~/.local/state/tele # session, local database and instance lock

ui:
  history_limit: 50 # messages fetched per chat on open
  confirm_quit: false # ask before q/ctrl+c/ctrl+q closes tele
  # theme: # omit for the built-in tele-dark / tele-light
  #   dark: my-dark # ~/.config/tele/themes/my-dark.yml
  #   light: my-light

  notifications:
    desktop: true # hand it to the OS notification service
    toast: true # draw it in a corner of tele's own window
    preview: true # set false to send the sender's name and no message text

  toasts:
    error_zone: bottom-right # bottom-right | top-right
    notify_zone: top-right # bottom-right | top-right
    max_visible: 3 # per corner; the rest are counted, not drawn

photos:
  mode: auto # auto | kitty | blocks - inline image renderer
  eager_full_quality: true # download full resolution in the background on chat open
  kitty_placement_cap: 16 # max inline images kept on the terminal at once
  max_long_side_px: 800 # cap a rendered image's long side; height also ≤ 2/3 pane
  disk_cache_size: 268435456 # 256 MB of fetched chat media kept between runs

avatars:
  disk_cache_size: 16777216 # 16 MB of people's pictures, budgeted separately

cli:
  name_width: 20 # columns a command gives a name or title before cutting it short
  account_commands: all # all | read | none: what commands may do with your chats

# keybindings: see keybindings.md
```

<a id="proxy"></a>
## Прокси

`proxy` определяет, как `tele` добирается до дата-центров Telegram.
Через него идёт каждое соединение: сообщения, фото, голосовые, файлы, из какого бы дата-центра они ни шли.
Раздел читается при запуске `tele`, который держит соединение, поэтому изменение вступает в силу после `[host restart]`.

`proxy.type` задаёт способ подключения и принимает четыре значения:

| `type`   | что делает                                                    |
| -------- | ------------------------------------------------------------- |
| `auto`   | по умолчанию: то, что задано в `ALL_PROXY`, а если там пусто, напрямую |
| `direct` | без прокси, `ALL_PROXY` не учитывается                        |
| `mtproto`| прокси MTProto: `server`, `port` и `secret`                   |
| `socks5` | прокси SOCKS5: `server`, `port` и `username`/`password`, если он их требует |

Прокси MTProto официальные клиенты берут из ссылок `tg://proxy` или `t.me/proxy`, включая локальные мосты, которые открывают такой прокси на `127.0.0.1`.
Пишите `secret` в том виде, в каком его опубликовал прокси: читается и hex, и base64url, и работают все три вида: простой секрет, секрет с `dd` и секрет с `ee`, который маскирует соединение под обычный веб-трафик к домену, записанному в секрете.

```yaml
proxy:
  type: mtproto
  server: 127.0.0.1
  port: 1443
  secret: ee0123456789abcdef0123456789abcdef6578616d706c652e636f6d
```

Копируйте секрет целиком, не разбирая его на части: в hex префикс `ee` и домен маскировки входят в одну строку (хвост в примере выше означает `example.com`), а в base64url весь секрет записан одним словом.

Прокси SOCKS5, который спрашивает, кто подключается, получает `username` и `password` вместе.
Одно без другого не принимается: с половиной логина соединению откажут без объяснения причин.

```yaml
proxy:
  type: socks5
  server: 10.0.0.1
  port: 1080
  username: me
  password: hunter2
```

Значения, относящиеся к другому типу, не трогаются, и о них сообщается при запуске: `secret` при `socks5` не используется, и `tele` говорит об этом, а не оставляет вас думать, что он используется.

<a id="when-the-proxy-does-not-work"></a>
### Когда прокси не работает

Если `tele` не может прочитать раздел прокси, он не запускается и выводит сообщение, где названы ключ, файл, в котором он записан, и единственная правка, с которой можно подключиться без прокси:

```text
config: proxy.secret is neither hex nor base64url; it is what a proxy publishes,
copied whole (in ~/.config/tele/config.yml; set proxy.type: direct to connect
without a proxy)
```

Если на прокси никто не отвечает, запуск останавливается точно так же, после одной попытки подключения с коротким тайм-аутом.
И то и другое происходит до того, как нарисован интерфейс, и это сделано намеренно.
Любую другую настройку в этом файле `tele` исправляет на значение по умолчанию и сообщает о ней предупреждением, но по умолчанию способ подключения означает прямое соединение с Telegram, а опечатка в секрете не должна молча отправить ваш трафик туда, куда прокси как раз не должен был его пускать.

Неверный секрет или неверные учётные данные невозможно отличить от недоступного сервера, пока не ответит Telegram, поэтому они проявляются как обычные ошибки соединения уже после запуска `tele`.

<a id="all_proxy"></a>
### ALL_PROXY

До появления этого раздела `tele` читал переменную окружения `ALL_PROXY`, и он по-прежнему читает её при `proxy.type: auto`.
Из неё берутся только адреса `socks5://`; прокси `http://` там игнорируется: всеми остальными программами молча, а `tele` с предупреждением.

Эта переменная устарела и будет удалена.
Она действует на все программы, запущенные из этой оболочки, а не только на `tele`, не умеет описывать прокси MTProto и не видна в окне настроек.
Перенесите её в конфиг:

```yaml
proxy:
  type: socks5
  server: 127.0.0.1
  port: 1080
```

<a id="state-directory"></a>
## Каталог состояния

`state_dir` задаёт, где лежит состояние аккаунта: сессия Telegram, локальная база данных и блокировка экземпляра.
По умолчанию это `$XDG_STATE_HOME/tele`, а если переменная не задана, `~/.local/state/tele`.

Каталог состояния одновременно держит только один `tele`: он поддерживает соединение с Telegram, сессию и базу данных.
Второй `tele`, запущенный с тем же каталогом состояния, не открывает их заново.
Вместо этого он подключается к первому как ещё одно окно того же аккаунта и использует его соединение.
Если закрыть второе окно, первое продолжит работать.
Если закрыть первое, закроются все подключённые к нему окна, поэтому, пока открыты другие окна, оно спрашивает перед выходом, что бы ни было в `confirm_quit`.
Окно, которое потеряло первый `tele`, сообщает об этом и при выходе печатает то, что было набрано в его поле ввода.

Окно, подключённое к другому `tele`, пишет лог в `tele-client.log` рядом с `tele.log`, с id процесса в каждой строке.

`tele`, слишком старый, чтобы к нему подключиться (1.11 или ранняя бета 2.0), по-прежнему держит каталог состояния, но не даёт к себе подключаться.
Более новый, запущенный рядом, ждёт несколько секунд, затем сообщает, какой процесс держит каталог, и завершается.
То же происходит, если два `tele` говорят на разных версиях протокола.
Завершите работающий и запустите снова.

<a id="running-without-a-window"></a>
## Работа без окна

`tele daemon` держит каталог состояния без собственного окна: поддерживает соединение, показывает системные уведомления и позволяет окнам подключаться к нему, пока вы не остановите его через Ctrl+C.
Он только держит каталог: если его уже держит другой `tele`, он называет того по версии и id процесса и завершается.

`tele daemon status` спрашивает у `tele`, который держит каталог состояния, как у него дела: его версию в сравнении с вашей, что поддерживает его работу, сколько он работает, сколько окон подключено, в каком состоянии аккаунт, есть ли связь с Telegram, когда пришло последнее обновление и сколько сообщений ждут отправки.
Команда завершается с кодом 0, если `tele` ответил, и с кодом 3, если не ответил никто.

`tele daemon --service` запускает менеджер сервисов, руками его набирать не нужно.
`tele`, запущенный так, не завершается, если каталог состояния занят: он ждёт и подхватывает каталог, когда держащий его `tele` завершится.

<a id="as-a-service"></a>
### Как сервис

`tele daemon install` поручает операционной системе поддерживать работу `tele`: он запускается при каждом входе в систему и снова, когда завершается.

- macOS: LaunchAgent в `~/Library/LaunchAgents`.
  Его собственный вывод идёт в `service.log` рядом с `tele.log`.
- Linux: пользовательский юнит systemd в `~/.config/systemd/user`; его вывод попадает в журнал.
  Linger не включается: сервис живёт, пока вы вошли в систему, а системное уведомление и так может дойти до вас только в это время.
- Windows: задача Планировщика заданий, которая запускается при входе в систему.
  Служба Windows работала бы там, где уведомление показать нельзя.
- В остальных системах устанавливать нечем; `install` подсказывает, как запускать `tele daemon` из своей сессии.

Сервис запускает `tele` так, как его находит ваш `PATH`, например `/opt/homebrew/bin/tele`, и никогда не файл конкретной версии за ним, чтобы обновление заменяло то, что он запускает.
Если `tele` в вашем `PATH` не тот, который вы запустили, `install` отказывается и называет оба; `--path` задаёт команду, которую запускать вместо него.
Со Scoop команда в `PATH` является прослойкой (shim), поэтому укажите её через `--path`.

На один файл конфигурации приходится один сервис.
Сервис запоминает конфиг, с которым его установили, и называется по нему, так что у беты и стабильной версии `tele`, как и у двух аккаунтов, сервисы свои.
Повторная установка заменяет сервис и запускает его заново, и так же можно указать ему `tele`, который переехал.

Если при установке каталог состояния держит какой-то `tele`, сервис ждёт и подхватывает его, когда тот завершится.

Первый `tele`, который держит аккаунт и в котором вы вошли в аккаунт, один раз спрашивает, установить ли сервис: `y` устанавливает его сразу, и сервис подхватывает аккаунт, когда этот `tele` завершится; `n` или Esc оставляют всё как есть.
Любой ответ запоминается, и вопрос больше не задаётся.
Он задаётся только там, где `install` сработал бы как есть: не задаётся без менеджера сервисов, когда `PATH` находит другой `tele` и когда сервис уже установлен.
Окно, подключённое к другому `tele`, никогда не спрашивает.

После обновления сервис продолжает работать на старой версии, пока к нему не подключится более новое окно: окно просит его перезапуститься, и менеджер сервисов запускает версию, установленную сейчас.
До тех пор `tele daemon status` сообщает, что версии различаются.
Ещё он предупреждает, если команды, которую запускает сервис, больше нет или если это другая версия, чем ваша.

`tele daemon uninstall` останавливает сервис и удаляет его.
Подключённые к нему окна получают сообщение, что он удалён.
Состояние и конфиг остаются как были.

<a id="windows-that-wait"></a>
### Окна, которые ждут

Окно, подключённое к сервису, ждёт его, когда он пропадает.
Примерно через две секунды в строке состояния появляется сообщение о переподключении; в поле ввода по-прежнему можно писать, а Enter сохраняет набранное вместо отправки.
Когда сервис возвращается, окно продолжает с того же места.
Через тридцать секунд оно перестаёт ждать и отсылает к `tele daemon status`; на Windows оно ждёт девяносто, потому что Планировщик заданий перезапускает сервис только через минуту.
Окно, подключённое к любому другому `tele`, не ждёт: тот `tele` был чьей-то сессией, и никто его не перезапустит.

Когда более новый `tele` подключается к более старому сервису, он просит сервис перезапуститься, и менеджер сервисов запускает его снова на версии, установленной сейчас.
Окно старше сервиса получает сообщение, что `tele` обновился, и закрывается; запустите его снова.
`tele`, который не является сервисом, извне никогда не перезапускается.

Если из аккаунта вышли или его заблокировали, пока не открыто ни одного окна, об этом один раз сообщается системным уведомлением, что бы ни было в `ui.notifications.desktop`: иначе узнать, что сообщения перестали приходить, нельзя.

Старый ключ `telegram.session_file` по-прежнему работает и держит сессию там, куда указывает, но он устарел и будет удалён в следующем релизе.
Если вы его не задавали, существующие сессия и база данных при первом запуске автоматически переносятся в каталог состояния: ничего не теряется, и вы остаётесь в аккаунте.

<a id="telegrams-limits"></a>
## Ограничения Telegram

Telegram ограничивает, как часто клиент может к нему обращаться, и тому, кто обращается слишком часто, отвечает требованием подождать (flood wait), прежде чем снова принимать такие вызовы.
`tele` заранее держится в пределах ограничений и соблюдает ожидания, когда они приходят:

- Все обращения к Telegram от всех окон и команд, подключённых к одному `tele`, расходуют один бюджет: до 40 сразу, затем 20 в секунду.
- Ожидание задерживает только тот вид вызовов, на который его получили: ожидание на загрузку истории не задерживает отправку.
- Работа, которую никто не ждёт (например, полноразмерные фото, загружаемые заранее (`photos.eager_full_quality`), и темы форумов, читаемые при подключении), оставляет треть бюджета тому, что делаете вы, и пережидает любое ожидание молча.
- Когда то, чего ждёте вы, упирается в ожидание от двух секунд, в строке состояния появляется «Telegram asks to wait» с обратным отсчётом.
  Ожидание до 45 секунд пережидается; о более долгом сообщается, а отправляемое сообщение остаётся в очереди и уходит, когда ожидание закончится.

Telegram не публикует свои ограничения, поэтому бюджет выше оценочный.
Если `tele` часто заставляет вас ждать или Telegram просит его подождать, когда вы не делаете ничего необычного, [откройте issue](https://github.com/sorokin-vladimir/tele/issues) и приложите `tele.log`.

<a id="notifications"></a>
## Уведомления

О новом сообщении вы узнаёте двумя способами, и `ui.notifications` включает их по отдельности.
`desktop` передаёт уведомление системной службе уведомлений вашей ОС: там оно видно, даже когда `tele` не на экране, и его может обработать ваш собственный демон уведомлений.
`toast` рисует его в углу окна самого `tele`, куда правила демона не дотянутся.
Можно выключить любой из них или оба.

Ни один переключатель не затрагивает список чатов: даже если оба выключены, новое сообщение подсвечивает строку чата и поднимает чат выше.
Это само сообщение пришло, а не вас отвлекают; ту же границу проводит и отключение уведомлений в самом Telegram.

`preview` отвечает за то, что говорит уведомление, а не за то, куда оно идёт, поэтому относится к обоим: если его выключить, и системное уведомление, и тост содержат только имя отправителя.
Текст уведомления формируется один раз и передаётся каждому без изменений, поэтому они никогда не расходятся насчёт одного и того же сообщения.

`ui.toasts` задаёт, где появляются сами тосты.
Ошибки, предупреждения и подтверждения появляются в `error_zone`, а уведомления в `notify_zone`.
Обе принимают `bottom-right` или `top-right` и могут указывать один и тот же угол; тогда тосты складываются в одну стопку.
Левый нижний угол не предлагается: он оставлен для показа нажатых клавиш.

<a id="photos"></a>
## Фото

`photos.mode` выбирает способ отрисовки.
`auto` использует протокол графики Kitty в терминалах, о которых известно, что они размещают изображения через символы-заполнители Unicode (kitty, Ghostty и iTerm2 начиная с 3.7.0), а везде остальном рисует блочную ANSI-графику, в том числе внутри tmux и screen, которые протокол не пропускают.
`kitty` и `blocks` принудительно выбирают один способ для терминала, который эвристика не знает: если принудительно включить `kitty` в терминале, который игнорирует символы-заполнители, на месте фото останется пустое место, а не блочная графика.
Значение читается один раз при запуске.

`kitty_placement_cap` ограничивает, сколько изображений Kitty одновременно размещено в терминале.
Передаются только изображения на экране (и несколько недавно прокрученных); более старые вытесняются.
Если передать весь тяжёлый чат сразу, можно превысить лимит изображений терминала и испортить размещение (фото сжимаются или съезжают); если вы всё ещё видите такое, уменьшите лимит.

`max_long_side_px` ограничивает длинную сторону изображения в чате в пикселях (как фиксированный размер медиа в десктопных клиентах).
Высота дополнительно ограничена двумя третями панели чата, чтобы высокое фото не занимало весь экран.
Увеличьте значение, чтобы изображения были крупнее, или уменьшите, чтобы они были компактнее.

<a id="avatars"></a>
## Аватары

`avatars.disk_cache_size` задаёт второй бюджет, намеренно отдельный от `photos.disk_cache_size`.
Аватар весит около сотни килобайт и запрашивается снова при каждом открытии профиля человека, а медиа из чатов не ограничены по объёму и просматриваются один раз; с общим бюджетом одна долгая прокрутка вытеснила бы все лица, что у вас есть.
Если любой из этих ключей равен `0`, это значит «ничего не хранить между запусками»: соответствующий кэш переезжает во временный каталог и удаляется при выходе.
